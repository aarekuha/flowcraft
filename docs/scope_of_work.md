# Flowcraft: черновик технического задания

## 1. Контекст проекта

`flowcraft` — внутреннее web-приложение для учета времени выполнения производственных операций.

Изначальный фокус проекта — производство изделий из кожи: сумки, кошельки, ремни и другие похожие изделия, состоящие из набора операций, которые выполняют разные специалисты.

Проект создается для внутреннего использования, без монетизации. Приоритет первого этапа — сделать минимально рабочую модель с понятными интерфейсами для сотрудников производства и бригадиров.

## 2. Цель MVP

Нужно создать web-приложение, которое позволит:

- вести учет времени на производстве;
- фиксировать рабочее время по типам активности;
- запускать учет простыми действиями с планшета, а в резервном варианте и со смартфона;
- назначать производственные этапы на конкретных исполнителей;
- запускать исполнение по конкретному заказу с указанием количества изделий;
- в дальнейшем строить статистику по времени операций, количеству изделий, простоям и загрузке сотрудников.

## 3. Основные принципы продукта

- Интерфейс должен быть простым, крупным и не перегруженным.
- На экране должны отображаться только те элементы управления, которые актуальны пользователю в текущий момент.
- Основной сценарий использования должен быть рассчитан на уставшего сотрудника, который работает руками и не должен тратить внимание на сложную навигацию.
- Ключевое действие должно выполняться через крупные кнопки, без сложных форм и лишних подтверждений.
- Система должна быть адаптирована под планшеты как основной тип устройства.
- Смартфон должен поддерживаться как резервный сценарий доступа.

## 4. Роли пользователей

### 4.1 Исполнитель

Исполнитель работает с таймерами и отмечает свою текущую активность.

Основные задачи:

- начать рабочий день;
- уйти на перерыв;
- отметить простой;
- запустить выполнение производственной операции;
- переключиться на другую операцию;
- завершить рабочий день.

### 4.2 Бригадир

Бригадир управляет производственными сущностями и назначениями.

Основные задачи:

- создавать шаблоны технологических процессов;
- создавать карточки изделий или производственных проектов;
- задавать дерево этапов и подэтапов;
- назначать исполнителей на этапы;
- указывать количество изделий при запуске в работу;
- наблюдать текущую загрузку команды и ход выполнения;
- просматривать статистику и отклонения.

### 4.3 Руководитель или наблюдатель

На первом этапе роль может совпадать с бригадиром, но архитектурно нужно предусмотреть отдельный интерфейс просмотра статистики и мониторинга.

## 5. Основные сущности

### 5.1 Изделие

Тип производимого объекта: кошелек, сумка, ремень и т.п.

### 5.2 Технологический процесс

Шаблон набора операций, необходимых для изготовления изделия.

Технологический процесс должен поддерживать:

- древовидную структуру;
- неограниченную вложенность этапов;
- детализацию до мелких подопераций;
- возможность назначения исполнителей на конкретные узлы дерева;
- возможность использовать один и тот же шаблон повторно.

Пример структуры:

```text
- Кошелек
  - Раскрой
    - Фасад
    - Карман
  - Пошив
    - Рамка
      - Внутренняя часть
      - Внешняя часть
    - Пришивание кармана
```

### 5.3 Производственный проект или заказ

Экземпляр запуска работы по конкретному изделию или партии изделий.

После создания проект должен:

- получить привязку к шаблону технологического процесса;
- содержать количество изделий;
- содержать назначения исполнителей;
- перейти в состояние, при котором доступен для взятия в работу;
- после запуска показывать исполнителям только доступные им операции.

### 5.4 Таймерная сессия

Запись о непрерывном интервале времени, в рамках которого пользователь выполнял один тип активности.

## 6. Типы таймеров

В MVP требуется поддержать следующие типы таймеров:

- начало рабочего дня;
- перерыв;
- простой;
- производственная процедура;
- конец рабочего дня.

### 6.1 Правила работы таймеров

- У сотрудника в один момент времени может быть активен только один таймер.
- Таймер нельзя остановить напрямую кнопкой `Стоп`.
- Текущий таймер завершается автоматически при запуске следующего таймера.
- Переход между состояниями должен происходить в одно нажатие или в минимально возможное число действий.
- Производственная операция запускается из набора доступных пользователю операций.
- `Простой` — отдельный тип активности для случая, когда сотрудник готов работать, но не может продолжать по внешним причинам.
- `Перерыв` должен охватывать обед, перекур и иные короткие остановки работы по инициативе сотрудника.
- `Начало дня` и `Конец дня` должны фиксировать рамки смены.

## 7. Пользовательские сценарии

### 7.1 Создание технологического процесса

Бригадир:

- создает изделие или шаблон изделия;
- задает дерево этапов и подэтапов;
- определяет возможных исполнителей или роли для этапов;
- сохраняет шаблон для повторного использования.

### 7.2 Создание проекта или заказа

Бригадир:

- выбирает изделие или шаблон;
- указывает количество изделий;
- назначает исполнителей;
- переводит проект в состояние готовности к исполнению.

### 7.3 Работа исполнителя

Исполнитель:

- открывает рабочий экран;
- видит только свои доступные действия;
- запускает `Начало дня`;
- выбирает и запускает доступную производственную операцию;
- при необходимости переключается на `Перерыв` или `Простой`;
- возвращается к работе запуском другой операции;
- завершает смену через `Конец дня`.

### 7.4 Мониторинг

Бригадир:

- видит, кто сейчас работает;
- видит, какой таймер у сотрудника активен;
- видит простои и перерывы;
- видит движение по заказам и этапам;
- в дальнейшем получает статистику по времени, количеству и загрузке.

## 8. Требования к интерфейсу

На основе текущего наброска `docs/ui_elements.jpg` в интерфейсе исполнителя нужно ориентироваться на следующие решения:

- в верхней части экрана располагаются крупные кнопки быстрых состояний;
- активный таймер визуально выделяется заметнее остальных;
- рядом с кнопкой или под ней отображается текущее накопленное время;
- ниже показываются доступные пользователю заказы, изделия и операции;
- при выборе изделия и количества сотрудник должен видеть только релевантные операции;
- иерархия операций должна раскрываться постепенно, без перегрузки экрана;
- крупные отступы и крупные зоны нажатия обязательны;
- контраст активного состояния должен быть высоким;
- основной экран должен быть пригоден для использования пальцем без клавиатуры и мыши.

### 8.1 Дополнительные UX-требования

- Минимизировать ручной ввод текста.
- Предпочитать выбор из готовых кнопок и списков.
- Избегать длинных таблиц на основном рабочем экране исполнителя.
- Приоритет отдать сценариям `один экран — одно текущее решение`.
- Ошибочное нажатие не должно приводить к потере истории.
- Должна быть понятная индикация, какой таймер идет сейчас.

## 9. Требования к данным и аналитике

Архитектурно нужно сразу предусмотреть накопление данных для последующей статистики.

Минимально необходимо сохранять:

- сотрудника;
- проект или заказ;
- изделие;
- этап или подэтап;
- тип активности;
- время начала;
- время завершения;
- длительность;
- количество изделий в проекте;
- назначенного исполнителя;
- причину простоя, если она будет добавлена позже.

На базе этих данных система в будущем должна позволить строить:

- длительность операций по каждому изделию;
- среднее время на этап и подэтап;
- статистику по исполнителю;
- статистику по заказу;
- статистику по простоям;
- сравнение плановых и фактических значений, если плановые нормы появятся позже;
- загрузку команды в разрезе смен, дней и периодов.

## 10. Нефункциональные требования

- Web-приложение.
- Корректная работа на планшетах в горизонтальной и вертикальной ориентации.
- Приемлемая работа на смартфонах как в резервном сценарии.
- Интерфейс должен открываться быстро и работать стабильно в локальной сети предприятия.
- Базовый аудит действий должен быть предусмотрен хотя бы на уровне ключевых событий.
- Архитектура должна допускать развитие в сторону отчетности и расширения производственных сценариев.

## 11. Предложение по стеку

### 11.1 Бэкенд

Рекомендуемый стек:

- `Python 3.12+`
- `FastAPI` для HTTP API
- адаптеры и интерфейсы доступа к данным, чтобы не привязывать бизнес-логику к конкретной БД
- `SQLAlchemy 2` + `Alembic` для работы с БД и миграциями
- `SQLite` как первичная реализация хранилища для MVP
- `Pydantic` для схем API

Почему это хороший старт:

- стек простой, распространенный и хорошо подходит под MVP;
- FastAPI быстро дает API, документацию и валидацию;
- подход через интерфейсы и адаптеры позволит позже без болезненной переделки перейти на другую СУБД;
- SQLite упрощает первый запуск MVP и снижает стоимость начального этапа;
- SQLAlchemy и Alembic дают управляемую схему данных без привязки к слишком магическим решениям.

### 11.2 Фронтенд

Рекомендуемый стек:

- `Vue 3`
- `TypeScript`
- `Vite`
- `Pinia`
- `Vue Router`
- UI-компоненты либо свои, либо минимальная библиотека без перегруженного дизайна

Почему выбирается `Vue 3`:

- проще войти в проект и поддерживать небольшой командой;
- удобен для интерфейсов с большим количеством состояний и форм;
- хорошо подходит для сборки компактного, понятного UI под планшеты;
- быстрее приводит к результату в административных и прикладных интерфейсах.

### 11.3 Дополнительно для MVP

Можно предусмотреть, но не обязательно включать в самый первый спринт:

- `Docker Compose` для локального окружения;
- `Nginx` как reverse proxy;
- простую cookie-based или token-based авторизацию;
- `pytest` для backend-тестов;
- `Playwright` для ключевых frontend-сценариев.

## 13. Границы MVP

В первый релиз рекомендуется включить:

- авторизацию пользователей;
- роли `исполнитель` и `бригадир`;
- создание шаблона технологического процесса;
- создание проекта или заказа на основе шаблона;
- назначение исполнителей;
- запуск и автоматическое переключение таймеров;
- основной экран исполнителя;
- экран мониторинга для бригадира;
- сохранение истории таймерных сессий;
- базовые отчеты по накопленному времени.

Во второй этап можно вынести:

- расширенную аналитику;
- причины простоя и классификацию простоев;
- нормы времени и план-факт анализ;
- уведомления;
- печатные формы;
- интеграции с другими системами;
- более сложное управление сменами и графиками.

## 14. Открытые вопросы

Перед переходом к детальному проектированию желательно уточнить:

- что является верхнеуровневой сущностью в терминах бизнеса: `изделие`, `заказ`, `проект`, `партия` или несколько сущностей сразу;
- должен ли один исполнитель одновременно быть назначен на несколько потенциально доступных операций;
- может ли одна операция выполняться сразу несколькими исполнителями;
- нужно ли учитывать количество выполненных единиц на уровне каждой операции;
- требуется ли фиксация брака, переделки и возврата на предыдущий этап;
- требуется ли офлайн-режим для планшетов;
- как именно должен выглядеть сценарий автоматического показа доступных таймеров из карточки заказа;
- нужна ли интеграция с кадровой системой или табелем рабочего времени;
- нужен ли журнал исправлений, если бригадир меняет историю задним числом.
